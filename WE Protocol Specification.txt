1. Introduction & Philosophy
The modern web is a clusterfuck. WE Protocol is the clean reset.
WE (Windowing Environment) is a server-authoritative hypermedia protocol that treats the client as a pure display + input engine. It reclaims the original hypermedia dream while using the power of your AiVectra display/windowing system:

Server owns all calculation, state, business logic, and semantics.
Client (AiVectra display engine) owns only rendering, vector scene graph, input capture, and deterministic layout.
No client-side JavaScript is required or allowed by default.
HTML is used only as a lightweight structural descriptor (regions, semantic markup). Everything visual is vector-first.
Communication is via thin, low-bandwidth IPC hooks (Unix sockets, named pipes, WebSocket, or HTTP/2+ streaming).
Widgets, icons, charts, and UI elements are sent as vectors or scene-graph commands — never raster PNGs/JPEGs.

Result: 10-100× bandwidth reduction, zero telemetry surface for big tech, native performance, and the ability to build complex applications exactly like your existing AiVectra windowing system already does.

2. Core Principles (Non-Negotiable)

Server is the single source of truth for logic and state.
Client is dumb and deterministic — it only applies updates to a retained vector scene graph.
HTML is markup, not behavior — no scripts, no inline event handlers that execute code.
Vector-first rendering — every visual element is a path, shape, transform, or retained object in the AiVectra scene graph.
IPC is the native transport — low-latency, bidirectional, low-overhead.
Bandwidth and latency are first-class citizens — deltas only, never full page reloads.
Telemetry loss is a feature — privacy win for users.


3. Architecture Overview
text[Server / Backend (AiLang or any language)]
        │
        │  (generates markup + vector commands)
        ▼
[IPC / WebSocket Channel]
        │
        ▼
[Client: AiVectra Display Engine]
   ├── Retained Vector Scene Graph
   ├── Deterministic Layout Engine
   ├── Input Event Dispatcher
   └── Region Manager (targeted updates)

Initial load: Server sends full HTML skeleton + root scene description.
Interaction: Client sends tiny event messages over IPC.
Update: Server replies with targeted fragment + vector delta commands.
Rendering: AiVectra applies updates natively to canvas/scene graph.


4. Transport Layer
Primary transports (in order of preference):

Unix Domain Socket / Named Pipe (local/self-hosted)
WebSocket (remote or browser)
HTTP/2 or HTTP/3 Server-Sent Events + POST (fallback)

Message format options (server chooses one per connection):

Binary (preferred for vectors) — custom compact format (see Section 6)
JSON5 / structured text (human readable for debugging)
CBOR (if binary but schema-heavy)

All messages are framed, versioned, and support compression (zstd or brotli).

5. Core Concepts
Regions
Named, addressable areas of the UI (like HTMX targets but native to AiVectra).
Example: <region id="main" role="dashboard"> or path-based /sidebar.
Actions
Server-defined verbs the client can trigger:

load, submit, click, change, poll, stream, custom:verb

Triggers
Client-side events that fire actions (click, input, timer, websocket message, etc.). Defined declaratively in markup.
Updates
Server responses can contain:

HTML fragment (for structure)
Vector command batch (paths, shapes, styles, transforms)
Scene-graph delta (add/remove/update nodes)
State patch (non-visual data)

Scene Graph
AiVectra’s retained vector scene graph. Every node has:

ID (stable across updates)
Transform matrix
Vector primitives (paths, text, gradients, etc.)
Deterministic layout constraints


6. Message Formats (Wire Protocol)
Event Message (Client → Server)
JSON{
  "version": "0.1",
  "type": "event",
  "action": "click",
  "target": "save-button",
  "region": "main",
  "payload": { "formData": {...} },
  "timestamp": "iso-string"
}
Update Message (Server → Client)
JSON{
  "version": "0.1",
  "type": "update",
  "region": "main",
  "html": "<div>...</div>",                  // optional structural change
  "commands": [                              // vector / scene commands
    { "op": "replace", "node": "id123", "data": { ...vector def... } },
    { "op": "transform", "node": "id456", "matrix": [1,0,0,1,10,20] },
    { "op": "style", ... }
  ],
  "delta": { ...optional binary delta blob... }
}
Binary vector command format (to be fully specified in v0.2 with AiVectra primitives).

7. Markup Extensions (HTML + WE Attributes)
Use standard HTML with these attributes (no JS):

we-action="submit"
we-target="main"
we-trigger="click|input|load"
we-region="sidebar"
we-vector="true" (hints that child content should be treated as vector description)

Server can return fragments that contain these attributes for progressive enhancement.

8. Example: Simple Todo Application
Initial HTML from server:
HTML<region id="todo-list">
  <ul we-region="items">
    <!-- populated by server -->
  </ul>
  <input type="text" we-action="add" we-target="items" placeholder="New task">
</region>
User types & presses enter → Client sends:
JSON{ "action": "add", "region": "items", "payload": { "text": "Buy milk" } }
Server replies with:

Updated HTML fragment for the list
OR pure vector commands to insert a new list-item node in the scene graph

No JavaScript. No bundle. No tracking.

9. Security Model

No arbitrary code execution on client (vectors are data, not code).
Sandboxed IPC channel (capabilities can be granted per connection).
Server controls all state transitions.
Optional signed commands for untrusted environments.


10. Extensibility & Future-Proofing

Custom action verbs
Plugin system for new vector primitives (WebGPU shaders, 3D nodes, etc.)
Streaming updates (live dashboards, collaborative editing)
Offline mode via local AiVectra caching rules (server-defined)


11. Migration Path from Existing Web

WE clients can embed legacy web views in a sandboxed region (progressive adoption).
Servers can serve both classic HTML + WE headers for dual support.


12. Reference Implementation Notes

Client: Your existing libraries/display (AiVectra) already does 90 % of this.
Server: Pure AiLang backend — just respond to events with fragments + vector commands.
Example apps: Todo, Dashboard, IDE, Chat, File manager — all already possible in your windowing system.
